## 一、总目标（迭代结束时必须同时成立）

| # | 目标 | 可验收判据 |

## 四、方法论提醒（这仓特有的坑）

1. **"绿了"不等于"装完能用"**：本仓的 zip 是好的（我实测四条命令全过），坏的是 pip 渠道。任何"可用性"结论必须写清是**哪个渠道**、**从哪个目录**跑的。
2. **修 `default_data_dir()` 时别把冻结态改坏**：`cli.py::handle_selftest` 有 `is_frozen()` 分支断言数据落在 `_MEIPASS` 内。装了包之后 `is_frozen()` 是 False，走的是源码态/装态分支——**这两条分支都要测**。
3. **`--check` 类工具会被写成"先写后比"**：本仓已经踩过一次（D5）。凡是"验证"命令，一律先确认它**不改磁盘**再加进门禁。
4. **门禁的子串判定**：`"hws-formal-math" in "hws-formal-math-viewer.exe"` 是 True。凡是"两个名字有前缀关系"的门，一律用 basename 精确比较 + 负控。
5. **`.gitattributes` 用 `*` 不覆盖子目录**：改完必须用 `git check-attr -a <二级路径>` 逐个回验，不能只看文件内容。
6. **EOL 在 Windows 上是隐形的**：本机 `core.autocrlf=true`。任何"字节一致性"门都要在 **LF 的 clone** 里再跑一次，否则会把 CRLF 当正确值固化下来。
7. **无 Lean 的环境里，skeleton 套件永远 `not_enabled`**：所以 `hws-formal-math bench`（不带 `--suite`）**exit 1 是设计行为**，不要"顺手"把它改成 0。要证明内核路径通了，必须有真 Lean 或可注入的假 `lean`。
8. **CI 证据要带 run id 与时间**：最近一次绿是 `39120882367` @ **2026-10-18T10:51:08Z**，早于 `ubuntu-latest → Ubuntu 26`（2026-10-19 起）。迁移后无任何运行——任何"CI 绿"的结论必须重新跑，不能引用旧 run。
9. **Python 3.8 与 `setuptools>=77`（PEP 639 SPDX license）不可兼得**：这是另一个仓（cninfo-watch）踩过的坑。若本批要转 SPDX，必须同时抬 floor。
10. **诊断与本批执行不要并行**：本仓 `update/` 已落盘；执行时若发现诊断结论有错，**在 `update/` 里写"更正 + 证据"，不要篡改上面的历史**。
